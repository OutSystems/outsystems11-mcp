# RFC: Customer audit persistence

## Business goal

Persist an auditable history of customer create, update, and delete events in the
currently open `BFUE_Monitoring` module.

## Functional requirements

- Add a `CustomerAudit` entity to store one audit record per event.
- Store the customer identifier as a 64-bit numeric value, the event/action, the
  changed-by user, the event timestamp, and before/after changed fields as
  serialized JSON.
- Limit each before/after JSON value to 2,000 characters, matching the
  supported text attribute length in this module.
- Add a reusable server action that callers can use to write an audit record.
- Keep the action private to `BFUE_Monitoring`; callers are within this module.
- Derive the changed-by user from the runtime identity. Background calls use
  their designated system identity.
- Set the timestamp when the server action persists the record.
- Support create, update, and delete audit events. For create events, before
  values may be empty; for delete events, after values may be empty.
- Validate both JSON input lengths and reject values over 2,000 characters
  before writing the audit row.
- Treat changed-fields JSON as an opaque caller-supplied value; callers are
  responsible for supplying valid JSON syntax.

## Acceptance criteria

- `CustomerAudit` is present in the module's data model with attributes for all
  required audit information.
- Calling the reusable server action creates a persistent `CustomerAudit` row
  with the supplied customer identifier, event/action, changed-fields JSON,
  runtime actor, and a server-generated timestamp.
- Invalid or incomplete inputs do not result in a success-shaped audit write.
- Unsupported event values and JSON values longer than 2,000 characters are
  rejected before the row is created.
- The action does not parse or validate JSON syntax.
- The module has no unrelated model changes and has no new validation errors.

## Scope

- The `BFUE_Monitoring` module currently has no `Customer` entity. Store the
  64-bit customer identifier as a value on the audit record rather than adding
  a relationship to a nonexistent entity.
- Add the audit entity and a reusable server action for recording entries.
- Callers are responsible for invoking the action for each relevant customer
  event and supplying the event and changed-fields JSON.

## Out of scope

- Creating a `Customer` entity or customer CRUD behavior.
- Automatically instrumenting customer create, update, or delete operations
  outside this module.
- Publishing the module.

## Risks

- The customer identifier's actual format and the appropriate OutSystems
  attribute types and lengths need confirmation during impact analysis.
- Before/after values may contain sensitive data; callers must avoid sending
  fields that should not be retained in audit history.
- Audit rows add persistent storage and require appropriate access controls and
  retention practices.

## Assumptions

- The agreed baseline is customer identifier, action, changed-by user,
  timestamp, and before/after changed fields as serialized JSON, with each JSON
  value capped at 2,000 characters.
- A caller-invoked reusable server action is the intended write path; there are
  no existing customer actions in this module to instrument.
- The timestamp is generated by the server when the audit row is written.
- The action is not intended for cross-module callers.
- Runtime identity accurately represents the actor for interactive and
  background invocations.
